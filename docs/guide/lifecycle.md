# Payment Lifecycle

Understanding the transactional lifecycle of Digipay UPG is critical for ensuring idempotent, double-spending-proof financial transactions.

```text
[ Merchant App ]                     [ Digipay UPG ]                     [ Customer ]
       │                                    │                                 │
   1.  ├──── Create Ticket (POST) ─────────>│                                 │
       │<─── Ticket & Redirect URL ─────────┤                                 │
       │                                    │                                 │
   2.  ├──── Redirect Customer ──────────────────────────────────────────────>│
       │                                    │<─── Enters Card/Wallet Details ─┤
       │                                    │─── Process Bank/PSP Auth ──────>│
       │                                    │                                 │
   3.  │<─── Gateway Callback (POST) ───────┤ (amount, trackingCode, rrn)     │
       │                                    │                                 │
   4.  ├──── Verify Purchase (POST) ───────>│ (MANDATORY CONFIRMATION)        │
       │<─── Verified Response (200 OK) ────┤                                 │
       │                                    │                                 │
   5.  ├──── (Optional) Deliver (POST) ────>│ (Required for Credit & BNPL)    │
       │                                    │                                 │
   6.  ├──── (Optional) Reverse/Refund ────>│ (Cancel or return money)        │
```

## Step-by-Step Breakdown

### 1. Ticket Creation
The merchant issues a ticket request with:
- `amount` (in Iranian Rials)
- `providerId` (unique order ID generated by merchant)
- `callbackUrl` (where Digipay should send the user after checkout)
- optional user `cellNumber`, basket breakdown, or gateway preference.

Digipay responds with a unique `ticket` and a `redirectUrl`.

### 2. Redirection
The merchant redirects the user's browser or mobile app to the provided `redirectUrl`. The customer completes the transaction using their Digipay Wallet, bank cards via IPG, or Credit/BNPL.

### 3. Gateway Callback
Upon transaction completion or cancellation, Digipay posts an HTTP request to your configured `callbackUrl`. The payload indicates whether the initial bank transaction succeeded (`result = "SUCCESS"`) along with a `trackingCode` and `rrn`.

### 4. Mandatory Verification
::: danger Unverified Transactions Expire
A transaction is **NOT complete** until the merchant actively confirms it by calling the `/purchases/verify` endpoint. Unverified transactions are automatically canceled and refunded back to the customer's card or wallet by Digipay!
:::

The merchant must verify that:
1. The payment status from the callback is `SUCCESS`.
2. The `amount` matches the internal database order amount.
3. The `providerId` matches the order in progress.
4. Calling `Digipay::verify()` returns `status == 0`.

### 5. Delivery Confirmation (Credit & BNPL only)
For Credit (`type: 5`) and BNPL installment purchases (`type: 13`), Digipay requires an additional fulfillment confirmation call to `/purchases/deliver` after the physical or digital order has been shipped or finalized.
